# Phase 02 Step 2 Test Coverage

## Scope
- **Depth**: Architectural, focused on the state interface split and trait boundary safety rather than detailed line-level behavior.
- **Crates**: `state` (source of the `StateDb` trait implementation), plus the future `state-memory` crate (expected to inherit the `StateDb` contract once carved out). Analysis also covers `app-evm` and `whirlpool-node` consumers that exercise the trait/impl pair.
- **Symbols**: The INTENT set — `StateDb`, `StateError`, `DBErrorMarker` impl, `DbAccount`, `InMemoryStateDb`, `DatabaseRef` impl, `Database` impl — each mapped back to existing tests and consumer usage.

## Consumer-level coverage
- **`app-evm`**: `EvmApplication` wraps a `StateProvider`/`revm::Database` implementation and uses it for genesis, propose, and verify. The `StateProvider` blanket impl (`crates/app-evm/src/traits.rs`) delegates to `StateDb`, so the tests in `crates/app-evm/src/executor.rs` (e.g., `propose_executes_transfer_transaction`, `propose_executes_contract_deployment`, `verify_accepts_valid_block`, `verify_rejects_wrong_state_root`, `verify_rejects_wrong_gas_used`) exercise the trait boundary during EVM flows. Each test funds accounts via `db.insert_account`, executes transactions, and checks computed roots/gas — ensuring that the split-trait still drives the right `commit`/`state_root` behavior and that the `revm::Database` wiring remains compatible. The `StateProvider` dependency also constrains the `DB` generics, so any trait re-export change would show there first. (See `crates/app-evm/src/executor.rs` around the `setup_app` helper and the async tests.)
- **`whirlpool-node`**: production code uses `TestStateDb` (defined in `crates/whirlpool-node/src/main.rs`) to wrap `InMemoryStateDb` and implement both `StateProvider` and `revm::Database`. There are currently no dedicated tests for the node binary, so coverage for this consumer implicitly comes from `app-evm`’s test suite plus the compile-time guarantee that `TestStateDb` still satisfies `StateProvider`/`Database`. Any regression in how `TestStateDb` delegates to `InMemoryStateDb` (e.g., forgetting to forward `commit` or `state_root` to the trait object) would only surface when the node is run; adding a lightweight integration test instantiating `TestStateDb` and a mock `ApplicationAdapter` would make the contract explicit before the split completes.

## Gaps & recommended tests
1. **Error path coverage for `StateError`**: The current tests never trigger the `Internal` variant, so the trait/impl split could introduce new failure modes undetected. Add a unit test in `state` that forces an error (for example, by mocking or wrapping `InMemoryStateDb` to return `Err(StateError::Internal)` from a `revm::Database` method) and verify that consumers propagate it cleanly.
2. **`TestStateDb` bridge exercise**: The node’s `TestStateDb` is untested; consider a simple integration smoke test that instantiates it, pins it behind `Arc<RwLock<_>>`, and runs a short `EvmApplication` propose cycle against it to prove the `StateProvider` + `revm::Database` delegation remains intact after the split and when the trait is exported from `state`. This test would also guard the transition to a separate `state-memory` crate.
3. **Trait export/consumer compile check**: Add a compile-only test (e.g., in `app-evm/tests` or a `trybuild` case) that depends on `state::traits::StateDb` rather than the concrete `InMemoryStateDb`. This will ensure future `state-memory` dependency reorganization doesn’t break the intended trait import path.
4. **`state-memory` future split**: Once `state-memory` exists, duplicate the `state` tests for the implementation in that crate to ensure the trait contract still holds; track this explicitly in test plans so the coverage matrix stays populated.

## Unknowns / assumptions
- **Assumed trait stability**: We assume `StateDb`’s method list (especially `state_root`, `commit`, and the `get_*` helpers) remains unchanged. Re-exporting the trait under `state::traits` must maintain these signatures for the downstream tests to continue compiling.
- **Error handling limited to success**: Tests exercise only the success paths of `revm::Database`/`DatabaseRef`, so we assume the split won’t introduce new failure handling requirements beyond the `StateError` stub defined here.
- **`state-memory` will mirror `InMemoryStateDb` semantics**: The future crate is expected to reuse the same tests (or clones thereof); until it exists, we rely on the existing `state` suite to signal regressions.
- **`whirlpool-node` coverage is transitive**: Because there are no node-specific tests, we assume that `app-evm`’s suite exercising `StateProvider` behavior suffices to notice most regressions that would also affect `TestStateDb`.
